# Observability — migration in progress

Implements the passive record/session/operation foundation and migration stages 2–9 from docs/OBSERVABILITY.md. The application shell owns one session and feeds existing runtime-error handlers, observed lifecycle transitions, navigation and accepted source/tune context into the bounded stream. Runtime errors have one authority; the legacy Bug Report projects its 50-entry tail from the stream. Perf run measurements are also authoritative in the stream; the old component run arrays are removed. Low-level parser/source/cache measurement owners remain intact.

Create a session explicitly at the application owner. Imports install no globals, listeners, observers, timers, persistence or implicit current-operation context. Carry operation handles/IDs explicitly across asynchronous and worker boundaries. Domain revisions and semantic fingerprints come from their existing owners.

Defaults: 20,000 records, 30-minute monotonic age, 4-MiB estimated serialized-byte budget, 2-KiB individual-record budget. The byte limit includes reserved repetition/emergency space; it is not an exact JS-heap or future persisted-export byte measurement. Expiry is enforced on write/snapshot/count queries, not by an idle timer. The shell allows 8 KiB per compact record to accommodate bounded Unicode runtime errors; total storage limits are unchanged. Constructor configuration is validated; record/clock/getter failures are contained by a reentry guard and fixed-size health counters.

Retention uses chronological and per-priority linked queues. Pressure evicts the oldest detail, then normal, before critical; lower-priority incoming records cannot evict higher-priority evidence. Critical-only pressure and age expiry may evict critical history, with counts exposed by status(). Consumers must surface these loss counters. They must not imply the retained tail is complete.

Consecutive detail records with equal compact content coalesce within a bounded window. Changing metadata, origin, operation or semantic fingerprint breaks the run. snapshot(), a changed record or a critical record flushes a coalescing summary with the omitted sequence interval/count. Interleaved unique storms remain bounded through retention, not an unbounded coalescing-key map. Optional bounded detection observes accepted/coalesced producer inputs inside the recorder; derived findings bypass its own detector and coalescing path.

Metadata is copied/frozen, limited to 16 scalar fields (64-character keys, 256-character strings). Compact envelope identity strings are bounded too. Oversized encoded records are rejected and counted. Operation handles retain the recorder's compact copy; never attach samples, tables, DOM nodes, errors, credentials or complete workspaces. Producers must explicitly select/redact fields. This layer does not classify sensitive strings for them.

Operation outcomes are success/failure/cancelled/superseded/stale, accepted exactly once. A completion after termination is separate async.completion.stale evidence. Children are linked explicitly and cannot begin from a terminated parent. Ending a session is idempotent and rejects new session operations/checkpoints; it does not cancel domain work. Existing handles may still publish terminal/stale evidence. There is no implicit domain teardown or application-state ownership.

The shell reuses the existing error/rejection listeners and owns three targeted pagehide/pageshow/visibilitychange listeners, with disposal on remount. BFCache suspension does not end a session; a nonpersisted pagehide records an observed end. Reload starts fresh; no prior-session persistence or crash inference is implemented. Accepted input evidence uses owner revisions and opaque reference identities without scanning samples or hashing domain objects. Detailed scope/invalidation/async producers remain a later stage.

The performance bridge publishes explicit scalar-only schemas in bounded multi-record measurements. Four fields per part accommodate worst-case JSON string escaping within the shell's 8-KiB allowance. A commit plus all parts is required for projection; partial measurements are omitted with loss evidence. Diagnostic strings retain up to 65536 UTF-16 code units through fragments; grouped diagnostics/slow reads retain at most 256 entries, with explicit truncation counts. Actual Blob probes currently supply only their existing five slow reads. No samples, cache columns or domain objects are serialized.

Perf queries select their latest run tails before reconstruction and cache one immutable derived read model. Recorder sequence/count and failure counters, with age expiry, determine validity. Three bounded resource signatures deduplicate unchanged snapshots only while that retained query is valid. This is a read cache, not a second mutable run authority. Clear resets the Perf lens with a stream event; a new load resets its channel/restore/decode lens. Old records remain subject to shared retention and its exposed loss counters.

Resource probes run at explicit Perf/report requests, never on a new polling timer. Raw Blob/cache diagnostic scope is captured for text reports; ordinary visible Perf rendering does not add Blob probe/sort work. Hidden completion updates record metrics without rebuilding Perf DOM. Completion timings are metrics from existing owners, not fabricated start/end operations; detailed cross-async/source correlation remains a later stage.

Parser reports and their prepared model now live in reports/parser-report.ts. The indicator retains one prepared view model borrowing the canonical ParserDiagnostic list, reusing its groups/integrity counters for explicit report actions. Consumers now import canonical Parser report functions directly; obsolete component re-exports are removed. The recorder stores only compact aggregate snapshots (counts/severities/recovery), never a truncated substitute for the full diagnostic list. Full current diagnostics remain available even after recorder eviction and are included in Bug Report on explicit request. Session reporting shows the latest retained summary per operation/source, bounded to 20 recent entries; it does not sum successive pending/validated snapshots.

At the existing file-input owner, explicit source.load operations span actual file handling. Source-object WeakMap associations carry operation identity into Logger publications/rebinding without an ambient current-operation slot. Staged success includes accepted CRC validation; main-thread success covers parse/acceptance, with workspace restoration remaining separately measured. Fallback stays in its original operation; explicit teardown/new-file selection marks cancellation/supersession. Existing domain cancellation/generation guards are unchanged. Instrumentation does not repair or prevent previously possible main-thread import races; detailed async-state ownership remains stage 5.

Batched IndexedDB persistence/recovery is installed at the shell; unified captured Diagnostics/export is installed; report/contract cleanup is complete locally. The recorder is not yet the sole authority for all diagnostics. See docs/HANDOFF.md for the exact local checkpoint and evidence.

Stage 5 adds explicit producer calls at existing Logger, Analyzer/VE, Histogram and persistence boundaries. `createOwnerEvidence` is a passive emitter/operation factory, not a wrapper around controllers; it installs no listeners, observers, timers or interception. Its owner IDs distinguish diagnostic producer instances and are not domain revisions. Revision/generation/active-state values come from the actual owners. State/no-op/render events use detail priority/coalescing; actual VE/Math/read/workspace/storage operations use explicit operation handles. Child domain generation events remain boundary events, not fabricated complete operations. Known input-event origins are preserved; unknown causes are marked system, not guessed user actions.

VE context/tune no-ops and hidden deferral are distinct from semantic invalidation/rebuild, actual tables/presentation scheduling, primary notifications and popup detail reuse. VE and Math handles terminate on the owner's existing cancellation/supersession and reject delayed completions into stale evidence without changing domain guards. Logger's source-bound context loader remains intentionally usable for its advertised source, even after replacement; its read operation measures combined elapsed read/assembly work rather than pure file I/O. Existing Perf metrics retain cache/physical-read distinctions.

Persistence evidence preserves getter acquisition, cached authority, error identity, save/remove order and retry counts. The INI definition cache records durable outcome after memory acceptance and the existing dispatch boundary, without introducing another cache or event. A failed write still leaves session data authoritative. Resource evidence uses existing lengths/listener/cache sizes at workflow boundaries; no full-log scans or process-wide DOM/resource polls were added.

`reports/owner-report.ts` exposes a bounded 30-record tail in explicit Bug Reports, including owner/generation/operation/outcome and coalescing evidence. It does not regenerate or record evidence itself. An ancestor-hidden Distribution completion is now observable; the existing completion behavior is preserved. Neither a hidden completion marker nor elapsed read time alone proves expensive CPU work or a freeze. Stage 6 therefore excludes these markers from same-state-work inference.

## Stage 6 — bounded anomaly evidence

The shell opts into `detectAnomalies: true`; standalone recorders remain disabled by default. Imports install nothing. `AnomalyDetector` is a recorder-owned scalar-state consumer, with no public subscription callback, application mutation, controller wrapper, listener, observer, timer, worker, storage or domain-array scan. It observes prepared accepted records and individual suppressed detail inputs, so recorder coalescing cannot hide repetition. Derived `anomaly.detected` records use stable `ruleCode` values, original evidence sequence ranges and available operation/owner/generation references. They are appended internally without recursive observation. Detector failures increment existing internal-failure accounting and do not change the producer's accepted record.

`health-rules.ts` owns the original seven health predicates and exact legacy wording/order. The pure `projectCurrentHealth` presentation lives beside these machine rules; the obsolete health component facade is removed. The existing 750-ms badge poll is still pure and does not record or scan history. Explicit report construction publishes ten scalar fields from its already acquired health snapshot; the detector applies the same policy and references that snapshot. The badge/issues/warnings still describe current legacy health. Historical anomaly counts do not become current errors.

Initial policy:

- `repetition.burst`: 100 matching component/diagnostic-owner/name/origin inputs in a 1-second window, including suppressed detail inputs. High event rate is not a CPU measurement or proof of unnecessary work. Performance metrics and recorder internals are excluded.
- `work.same-state`: three eligible successful-completion/rebuild boundaries within 1 second with identical complete owner-provided semantic fingerprint and source/tune/state identities. The allowlist is `ve.rebuild`, `analysis.completed`, `render.completed`. Fingerprints at the 128-character envelope truncation bound are conservatively excluded. Switching semantics resets the window. Current VE render/rebuild boundaries do not supply a complete fingerprint, so this rule deliberately does not infer equivalence from their revisions alone. Requests, no-op deliveries, Result View/presentation rendering, cache hits and hidden completion markers are not eligible. The rule's opt-in capability is tested with synthetic owner sequences; no new full-state hashing or producer is added to make it fire.
- `async.stale-completion`: actual explicit stale-operation, domain/comparison/read or delay-generation markers yield informational evidence. These often prove that a healthy rejection guard worked; they do not prove an obsolete result was accepted. Existing operation outcomes remain unchanged.
- `async.unfinished`: on explicit session report request only, a tracked start at least 30 seconds old with no observed terminal produces informational evidence once. This is an observation threshold, not an application timeout, CPU duration, crash inference or cancellation. Awaited I/O, suspension and missed terminals remain possible. All five terminal outcomes remove pending tracking. No timer or full-history reconstruction is used.
- `persistence.session-only`: actual false persistence feedback, or INI memory acceptance plus durable failure/unavailability, yields warning evidence of session-only changes. It does not accuse the application of reporting success: existing visible failure/retry behavior is preserved. Adapter failure alone does not imply memory changed. Success does not erase historical evidence.

Each of the burst, semantic, pending-operation and cooldown maps has at most 128 entries. Pending state retains compact identity only, not producer payloads. FIFO tracking eviction is counted separately from recorder retention. Findings are limited to 16 per 1-second window and one per rule/component/owner/operation per 60-second cooldown; rate-suppressed findings are counted. Bounds may lose patterns, especially under storms. Explicit reporting prints tracking loss and suppression alongside ordinary recorder loss; evidence is not complete history. Policy thresholds are diagnostic constants, never application scheduling decisions.

`reports/anomaly-report.ts` projects the last 30 retained findings into the existing Bug Report. Sequence references may point into coalesced or evicted evidence, and a historical unfinished/stale/persistence finding can remain after successful recovery. Cycle reconstruction, hidden material-work attribution, resource trends, unexpected physical I/O, workload-relative CPU baselines and previous-session termination inference are deferred until adequate owner evidence/persistence exists. No original freeze diagnosis or large-log speedup is claimed.

## Stage 7 — local batched black box

`session-persistence.ts` is owned by the existing shell session, independently of Logger/source/tune/workspace storage. The shell constructs it once and reuses existing visibility/pagehide/remount boundaries. It owns one 30-second interval and disposes it; no new global event listener/observer or per-record subscription is installed. Startup restoration is asynchronous and does not gate mounting/navigation. One initial batch, periodic batches and existing lifecycle boundaries request persistence. Overlapping requests share an in-flight write plus one latest follow-up; batches never overlap. Idle heartbeats update the compact summary index only, without snapshot reconstruction or rewriting event bodies. Retained evidence is refreshed when new records arrive or its record-age deadline passes.

`persistence.ts` implements the internal `SessionStore` contract with lazy version-1 IndexedDB (`epicscope.observability`, `summaries`/`evidence` stores). IndexedDB is an adapter rather than an event-history localStorage contract. The summary index carries payload bytes and last-seen state, so normal writes/pruning do not load other sessions' full event bodies. Each save and retention deletion is one transaction across both stores. Concurrent tabs use separate session keys and serialized transactions; they do not overwrite one shared manifest. Other active tabs may still appear as unconfirmed recorded sessions. Startup recovery is a bounded startup snapshot, not a live cross-tab dashboard.

`retention.ts` selects at most 5000 compact records per session within 1 MiB UTF-8 JSON payload, reserving framing/summary/window space. The store retains at most four sessions (current plus up to three others), with a separate 5-MiB total payload ceiling and seven-day last-seen/record-age limits. At these conservative per-session limits the combined evidence is normally below 4 MiB. These are serialized payload bounds, not exact IndexedDB disk overhead or JS-heap measurements. Expiry occurs on load/save/periodic batch, without an additional cleanup timer. Unsupported external rows are never deleted to make unknown schema data appear valid.

Up to eight recent anomaly/error triggers retain up to ten available records before/after each event. Context materialization is bounded while selecting, not only after collecting every error window. Trigger records and the newest 20 records take precedence over additional context, then the remaining recent tail fills the budget. Context beyond ring/byte/count retention may be absent; coalesced sequence intervals are not expanded into invented records. Selected windows survive later current-ring/tail rollover until replaced/expired. There is no per-event capture/write; evidence lost from the recorder before a batch cannot be recovered. A writer-local weak size cache reuses immutable record sizes without retaining evicted keys.

Compact summaries retain session start/lastSeen/last sequence, observed end, active view, completed operation, checkpoint and observed error/anomaly/loss counts. Counts are derived from retained new records at batch time and can miss evidence already evicted; they are not complete lifetime totals. A failed write retains the pending body as dirty, even when replacing an older durable batch. Retry is through later batches; write success is accepted only after transaction completion. One bounded `observability.persistence.failed` event per failure episode and one recovery event use the internal subsystem, preventing recursive anomaly/storage storms. Read/unsupported-schema failure disables writing for that session; a new healthy session can recover. Current in-memory diagnostics and domain state keep working. Close failures are contained too.

Recovery validates schema, identity, sequence ordering, scalar fields/metadata, byte/count/window limits and index/body agreement. Version 1 is the first persisted format; there is no earlier format to migrate by guessing. Newer database/payload versions and corrupt rows fail closed without destructive reset or silent rewrite. Normal writes never downgrade a newer index. Expired valid sessions are pruned transactionally. No recovered record is inserted into the new recorder, runtime-error count or domain models.

The existing Bug Report adds `reports/previous-session-report.ts`: up to three summaries, final 20 records and up to three retained neighbors around each selected trigger. This is an explicitly bounded view of recovered evidence, with session/operation identity and available error messages. It labels `confirmed-normal-end` only when the committed summary observed the owner's existing end record. Otherwise it reports `unconfirmed-no-end-observed`, which does not establish application crash causality and may describe another active tab. The initial report can show loading/failed state; reopening after asynchronous recovery projects the available data. Unified/live Diagnostics UI remains stage 8.

Lifecycle transactions are best effort: a renderer/browser/OS may terminate before the final write commits. Periodic summaries provide an earlier last-seen boundary; they cannot guarantee the latest uncommitted events or power-loss durability. Tests actually terminate the Chromium renderer after a committed visibility batch, then reload in the same browser context. Whole-browser/OS termination, real BFCache eligibility, original ~1.2-GB recording and target-hardware latency/heap acceptance remain separate unverified cases. Synthetic bounded-event timings include transaction wait and must not be reported as pure CPU or file I/O.

## Stage 8 — unified captured Diagnostics and export

The shell's existing Report entry now presents **Diagnostics** with ten lenses: Health, Timeline, Operations, Anomalies, Performance, Parser, Resources, Errors, Previous session and Export report. `diagnostics.ts` defines the explicit capture and pure filtering/operation projections; `components/diagnostics-view.ts` owns local controls/pagination. Opening or explicit Refresh captures current health, owner-provided Perf probes/projection, canonical Parser report/list, one prepared recorder snapshot, retention/anomaly tracking and recovered-session status/history. Runtime/session report lenses accept that prepared record snapshot instead of querying/checking again. Capture DTOs exclude source/tune/workspace/raw log objects. Parser messages/recovery/offsets remain complete and copied for stable export.

View switches, filter changes, pagination, copy and export reuse the retained capture. They do not call controller context/tune/refresh methods, read traces, run analysis or collect probes again. There is no polling, observer or record subscription for the UI. New control/keyboard listeners are local to Diagnostics; existing transient-surface closing and shell disposal abort its export. Current health remains separate from historical anomalies/previous errors. Stage 9 removed compatibility formatter/health/re-export ownership while retaining useful compact Perf/Parser views as projections of the same authorities. Users can access all evidence through Diagnostics without relying on them; frozen compact UI/report features remain intact.

Timeline/Anomalies/Errors/Operations filter the bounded captured stream by subsystem, component, operation, origin, severity, active/hidden, record kind, outcome, source/tune revision, anomaly code and name/reason/operation/code search. Exact filters combine with AND. Chronology is preserved, page size is 200, and controls show total matches/page/loss. Operation relationships are projected lazily once per capture with linear iterative traversal: parent IDs, actual terminal outcome/elapsed duration and stale count remain explicit. Missing starts/parents are marked; cyclic relationships terminate safely. Visual indentation is capped while exact parent IDs/full depth remain in the projection. Filtering may omit a visible ancestor; it does not invent a missing historical parent. Elapsed time is labelled as distinct from CPU.

Perf text retains the existing formatter and cached physical/cache/decode distinctions. Resources uses the same captured Blob/decode/memory projection rather than parsing English report strings. Parser retains the complete canonical report plus full structured diagnostic list, including entries beyond the compact indicator's UI cap. Previous session uses the existing bounded black-box report and unconfirmed-end qualification. Full report text remains available in Export report. Escape closes Diagnostics locally/restores trigger focus; clipboard denial reveals/selects the captured full text for manual copy.

`export.ts` creates a standard two-entry ZIP (`report.txt`, `observability.json`) with matching captured timestamp/session/evidence. JSON includes exact record relationships, retention/anomaly/persistence loss/state, current health, complete current Parser diagnostics, Perf/resource evidence and bounded previous sessions. UI filters/pages never truncate export. It is explicitly full local diagnostics and can include filenames, environment details, messages/stacks; it does not silently attach raw MLG/MSQ/INI contents or transmit anything. Existing text export/copy reuse the same captured report. No external ZIP dependency was added.

ZIP CRC work yields every 64 KiB and checks a job-local AbortSignal. Closing/toggling/outside dismissal/remount or Refresh aborts obsolete export; no URL/download is published after cancellation at its next checkpoint. URLs are revoked and buttons restored. There is no persistent export timer/poll, global event listener, worker or domain lifecycle wrapper. JSON serialization/text encoding and initial snapshot/Parser copying still run synchronously on explicit capture/export; very large canonical diagnostic lists remain a target-hardware profiling case. Stored ZIP entries trade larger downloads for simple bounded chunk processing; this is not a compression or memory-budget guarantee. Exports are explicit artifacts outside automatic session-retention pruning.

Acceptance includes pure malformed/deep-history/filter/export regressions, a 20001-record browser view with at most 200 DOM rows, real-shell lens switching without extra source/context/VE work, native Chrome ZIP downloads, independently verified CRC/text/JSON identity, cancelled second export and local Escape focus. Prior Perf/Parser/controller/persistence/browser checks remain. Original large-recording/target-hardware, OS-level crash and real BFCache acceptance are still unverified; no speedup/CPU-free guarantee is claimed.

## Stage 9 — authoritative ownership cleanup

`capture.ts` is now the single explicit report assembly boundary. The shell supplies its owned source/workspace/application context and actual-owner prepared Perf/Parser/persistence evidence. The coordinator derives current health from the same recorder, records one compact health snapshot, checks anomalies once, obtains one report snapshot and uses it for runtime/session/report/export capture. It does not wrap controllers or read/recompute domain data. The pure badge projection is shared at `health-rules.ts` and does not record/scan history. The shell no longer assembles separate health/Perf/Parser/runtime/session/recovery reports itself; its existing badge interval is explicitly cleared on remount.

`reports/runtime-report.ts` owns the unchanged complete runtime text formatter/types. The former `components/bug-report-formatter.ts` and `components/bug-report-health.ts` are deleted, with direct consumer imports and no re-export shims. `performance-types.ts` owns unchanged measurement contracts, eliminating producer/report/test type imports from the Perf DOM component. Parser report functions are imported directly from their canonical module rather than re-exported by the indicator. The old report/health/Parser unit files are renamed to match these projection responsibilities; all assertions remain, plus coordinator tests.

Earlier stages already eliminated the parallel error array and Perf run stores. Stage 9 does not invent another store/cache or delete healthy retained canonical Parser data, physical/decoded/source cache measurement owners, bounded projections or storage. Compact Perf/Parser views remain useful presentation, with exact pre-migration rich Perf UI/text and full Parser evidence parity. They are not duplicate authorities: all metrics/history/formatters come from the shared model, and their presentation/clear/copy semantics remain. The full Diagnostics surface remains the coherent report/export entry.

Required migration stages 1–9 are implemented locally. Optional stage 10 baseline intelligence is not automatically started. Browser/unit/build parity does not replace original ~1.2-GB MLG, target-machine latency/heap, real BFCache or whole-browser/OS recovery acceptance. No performance speedup or deployment/publication is implied by this cleanup.

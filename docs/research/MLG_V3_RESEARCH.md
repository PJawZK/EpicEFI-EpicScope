# MLG v3 compatibility research

## Purpose

This was a deliberately bounded side-track to determine whether EpicScope's MLG parser would need a new architecture for v3 or only a compatibility extension.

Research references:

- TunerStudioMS 3.6.00.06 Beta package;
- MegaLogViewer HD 4.6.14;
- a real bench log generated by the TunerStudio beta;
- controlled synthetic v3 fixtures opened in MLV.

The goal was compatibility understanding, not copying EFI Analytics implementation details.

---

## TunerStudio beta package

Uploaded package:

- `TunerStudioMS_v3.6.00.06_Beta.tar.gz`;
- SHA-256: `2c351930ed26c7226a507e5224c5f1a4087b04a6d460911d0054aa4b61685463`.

Relevant classes/resources confirmed that the reader recognizes format versions through 3.

Observed outer-layout behavior:

- v1 uses the older fixed header / shorter field descriptor form;
- v2 and v3 share the extended header/descriptor size path;
- the reader rejects versions above 3.

This strongly indicates v3 is an extension of v2 metadata/data encodings rather than a new container architecture.

---

## Real beta-generated bench log

Reference log:

- `2026-10-13_11.20.57.mlg`;
- generated by the 3.6.00.06 beta on the bench.

Observed header:

```text
magic:          MLVLG
format version: 2
record length:  4689 bytes
field count:    1788
```

All 1788 field descriptors used only legacy scalar IDs:

```text
0: 468 fields
1:  29 fields
2: 300 fields
3: 186 fields
4: 491 fields
5:   8 fields
7: 306 fields
```

No v3-only encoding appeared.

Conclusion:

> A v3-capable TunerStudio does not automatically write every log as v3. If the project can be represented entirely by legacy encodings, the beta continues to write v2.

This means EpicScope v3 support is a compatibility expansion, not a current blocker for the observed EpicEFI project/log set.

---

## Ordinary INI syntax does not provide a simple v3 trigger

The normal ECU `[OutputChannels]` type syntax exposed by the beta/manual remains focused on the legacy runtime scalar types. The `[Datalog]` float/int field is no longer the binary-storage selector that could be used to force a v3 encoding.

Therefore a normal EpicEFI INI could not cleanly be modified with something like `scalar, F64` merely to force a v3 log.

This was an important reason to use controlled fixtures rather than perturbing the real ECU definition.

---

## Synthetic v3 fixture validation

A minimal v3 file using the v2-sized outer layout was generated and opened successfully in MLV 4.6.14.

That confirmed the basic v3 container assumptions were valid:

- `MLVLG` magic;
- version = 3;
- v2-style extended header;
- 89-byte field descriptors;
- normal record block/checksum structure.

The first multi-field probe also exposed that MLV's handling of some new field widths/offsets was incomplete/quirky enough that isolated one-field probes were needed for reliable type testing.

---

## Confirmed scalar descriptor IDs

Controlled one-field v3 probes established that MLV 4.6.14 accepts and decodes scalar IDs 9 through 14 while rejecting IDs 8 and 15 as unknown LoggerField types.

Confirmed on-disk scalar family:

| ID | Meaning | Width | Byte order |
|---:|---|---:|---|
| 0 | U08 | 1 | n/a |
| 1 | S08 | 1 | n/a |
| 2 | U16 | 2 | big-endian |
| 3 | S16 | 2 | big-endian |
| 4 | U32 | 4 | big-endian |
| 5 | S32 | 4 | big-endian |
| 6 | S64 | 8 | big-endian |
| 7 | F32 | 4 | big-endian |
| 8 | invalid / rejected by tested LoggerField path | — | — |
| 9 | U16 | 2 | little-endian |
| 10 | S16 | 2 | little-endian |
| 11 | U32 | 4 | little-endian |
| 12 | S32 | 4 | little-endian |
| 13 | S64 | 8 | little-endian |
| 14 | F32 | 4 | little-endian |
| 15 | invalid / rejected by tested LoggerField path | — | — |

The isolated probes used known values such as:

- ID 9 LE U16 -> `4660`;
- ID 10 LE S16 -> `-1234`;
- ID 11 LE U32 -> `305419896`;
- ID 12 LE S32 -> `-1234567`;
- ID 13 LE S64 -> `-1234567890123`;
- ID 14 LE F32 -> `-2.5`.

The user confirmed all non-candidate probes opened and produced visible values; IDs 8 and 15 were the two rejected candidates.

---

## F64 status

Internal EFI Analytics type infrastructure inspected during the investigation contained double-width/F64-related concepts, which initially suggested IDs 8/15 might represent BE/LE F64.

Controlled MLV testing disproved that projection for the on-disk LoggerField namespace:

- ID 8 was rejected;
- ID 15 was rejected.

Therefore EpicScope must **not** assign F64 semantics to those descriptor IDs merely because a shared internal enum/classifier contains double-width types.

Current conclusion:

> F64 on-disk LoggerField encoding remains unresolved for the exact software versions tested and should not be invented in EpicScope.

If a future authoritative specification or real v3 file contains F64, support can be added from that evidence.

---

## Bitfield namespace

The inspected v3-capable descriptor logic recognizes an extended bitfield range in the 16..20 area.

The broad compatibility implication is that EpicScope's old v1/v2 bitfield type model cannot be assumed complete for v3.

Exact bitfield encode/decode behavior should be validated with fixtures before production support is declared. Scalar v3 compatibility was the higher-value immediate finding.

---

## Container conclusion

The central architectural result is:

> MLG v3 is not a new parser architecture. It is effectively the v2-style container plus expanded numeric encodings / field-type semantics.

Therefore EpicScope should eventually extend its current parser by:

- accepting version 3;
- representing per-field byte order explicitly;
- supporting confirmed little-endian scalar IDs 9..14;
- extending/validating the v3 bitfield family;
- explicitly rejecting unknown/reserved IDs such as 8/15 until evidence says otherwise.

It should **not** fork into an unrelated v3 parser unless future evidence shows a truly different record structure.

---

## Suggested parser architecture

Rather than growing ad-hoc type switches, represent a decoded field type as metadata such as:

```text
widthBytes
numericKind = unsigned | signed | float | bitfield
endianness = big | little
```

Then decode through a common numeric reader.

This reduces the risk of future format extensions becoming a collection of special cases.

---

## Regression requirements when v3 support is implemented

At minimum add fixtures/tests for:

- version-3 header acceptance;
- LE U16;
- LE S16;
- LE U32;
- LE S32;
- LE S64;
- LE F32;
- mixed legacy + v3 fields in one record;
- exact field-offset accumulation across mixed widths;
- CRC/checksum behavior unchanged from v2-style records;
- reserved/unknown descriptor IDs rejected explicitly;
- v3 bitfields once their exact mapping is validated;
- real v2 logs continuing to decode identically.

The mixed-field offset case deserves special attention because the original combined experimental fixture exposed implementation quirks in MLV that isolated one-field probes avoided.

---

## Research status

The v3 side-track is complete enough for current EpicScope planning.

Known:

- v3 exists and is accepted by current EFI Analytics tooling;
- v2/v3 share the same broad outer container path;
- ordinary current EpicEFI logs can remain v2 even in a v3-capable TunerStudio;
- LE scalar IDs 9..14 are experimentally confirmed;
- IDs 8 and 15 must not be assumed to be F64;
- EpicScope needs a compatibility extension, not a parser rewrite.

Still intentionally unresolved:

- exact on-disk F64 representation for the tested generation;
- fully fixture-validated mapping of every extended bitfield type.

Those remaining items are not blocking current EpicEFI log support and should only be revisited when a real compatibility need appears.

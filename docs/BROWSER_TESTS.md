# Browser acceptance

From the repository root, with the locked npm dependencies installed and a local Chromium or Chrome executable:

```sh
npm ci
CHROME_BIN=chromium npm run test:browser
```

`CHROME_BIN` defaults to `chromium`; use an executable name on PATH or an absolute path. No browser download or extra npm dependency is required. On a trusted container/CI runner that cannot use Chrome's sandbox, explicitly set `CHROME_NO_SANDBOX=1`. Ordinary desktop runs should retain the sandbox. Node must meet package.json's engine requirement. The npm command enables Node's built-in WebSocket transport explicitly for the supported Node 20 line; it also works on Node 22/24 without another transport dependency.

The command starts its own loopback Vite server and headless Chrome on dynamically allocated ports. It creates a temporary Chrome profile, uses separate incognito contexts for staged and forced Worker-disabled fallback imports, and closes its contexts, Chrome and Vite before removing the profile. It does not connect to an existing browser or application server. Ctrl-C and SIGTERM follow the same cleanup path. Each run has a ten-minute deadline, with bounded DevTools and readiness waits.

The observability foundation module constructs a standalone recorder; it does not install application producers. It checks explicit operation correlation/terminal and stale evidence, a 100k detail-event storm with bounded storage/error preservation and unchanged application state, compact metadata copies, byte limits and session end. Small recorder-on/minimal-off call-cost observations are saved as measurements, not timing pass/fail assertions or proof of integrated application overhead.

Target 18 uses a controlled injected socket/scheduler and browser-native Blob support. Deferred successful/rejected/corrupt conversions settle after manual disconnect or replacement; the replacement deliberately reuses stream ID/generation. No old telemetry/error/state change may publish, and the new ArrayBuffer frame must still arrive. Changed-generation corruption is rejected before decode, and current native Blob success/error behavior is retained. Before the fix, Chromium actually observed old and current values `[111, 222]` instead of `[222]`. These are controlled browser transport fixtures, not a live ECU/WebSocket-server or packet-loss stress test. Default transport remains ArrayBuffer; this does not diagnose original file-load freezes.

Stage 9 cleanup keeps the complete frozen Perf UI/text and canonical Parser checks unchanged. Report/capture unit tests now import observability projections directly; no deleted compatibility module is needed. Native download/CRC/cancellation, controller/source lifecycle and renderer recovery checks remain in the same suite. Compact views retain their useful features while sharing authoritative evidence/formatters.

Diagnostics component checks use 20001 captured records, including a deep operation chain and HTML-like event text: no more than 200 safe rows may render, paging/filter counts must be correct, and all ten views reuse the capture. Real-shell checks cycle every lens without recording/reprobing/rereading/reanalyzing; Chrome downloads the ZIP to a runner-owned directory. Its text and structured session/record/Parser/resource identity must match the capture. A second pending export is cancelled by closing, without another file; Escape closes locally and restores focus. Downloads/screenshots remain with browser artifacts. Unit checks independently verify ZIP CRC/local/central/end records and complete structured Parser messages; the downloaded ZIP can also be validated with standard zip tooling. Views do not establish original-large-log/target-hardware acceptance.

Persistence checks exercise a separate native IndexedDB database: reopen with tail/context, summary-only heartbeat puts, current-plus-three session retention, byte/age limits, quota-fault transaction abort/recovery and unsupported database/payload versions without reset. A 20000-event diagnostic storm measures cold/idle/update batches with no timing assertions. After ordinary shell acceptance and fresh-session checks, CDP actually terminates the renderer, reloads and verifies committed previous evidence as unconfirmed; a committed normal end is separately recovered as confirmed. Preload IndexedDB getter denial must preserve navigation/current diagnostics and expose failure; healthy reload restores access without clearing history. The crash test deliberately waits for a visibility batch to commit: it does not promise recovery of uncommitted events, whole-browser/OS crash durability or real BFCache eligibility.

Readiness polling retries only DevTools context/navigation-replacement errors. JavaScript assertions/application failures remain fatal. The foundation storm uses a controlled monotonic clock for its exact within-window coalescing assertion; duration observations still use real performance time.

Anomaly checks enable the detector explicitly in a standalone session and exercise actual retained VE updates/cancelled late work and existing save/retry feedback. Clock-controlled unfinished work is evaluated only by explicit report generation; it can still finish successfully afterward. A 2000-operation stale storm must cap derived records and expose suppressed coverage. Alternating enabled/disabled 5000-call recorder measurements are observations without timing thresholds. Integrated shell checks require scalar health evidence and the anomaly report alongside original Perf/owner reporting, with no extra Logger trace load or context publication. These checks do not establish original-large-log or target-hardware performance.

Owner-evidence checks use the existing VE lifecycle fixture with an explicit recorder: successful analysis, unchanged updates, popup build/reuse, presentation-only Result Views, hidden cancellation and semantic supersession with delayed stale completions. They exercise a delayed Math preview, exact persistence feedback/retry calls and actual shared Logger/read/workspace/VE/storage evidence after real file loading. A pending Distribution completion is observed after an ancestor is hidden, preserving its existing acceptance behavior rather than claiming new cancellation. A small alternating enabled/disabled 5000-call emitter benchmark saves observations without timing assertions; it is not a large-log or process-heap benchmark. The owner tail must be available in Bug Report.

Parser migration checks compare exact report text, indicator severity classes and UI text against four pre-stage-4 fixtures: empty, pending/retry recovery, CRC/counter anomalies and a fatal/long-message case with 45 warnings. They require the owner-cached report to equal the complete canonical formatter, including findings beyond the 40 visible occurrence rows. After actual INI/MSQ/MLG imports and VE analysis, summaries must link to the real source load start/success operation in both staged and fallback paths, and Bug Report must include the full current Parser report plus correlated session summaries. These checks do not claim corrupted-file worker fault injection, original large-log acceptance or new stale-domain-completion prevention.

Performance migration checks first compare complete deterministic text/UI against `performance-parity.json`, frozen before the stage-3 bridge. They distinguish cached CPU/render work from physical reads, check hidden DOM stability and clear/new-load lens boundaries, and record 1800 completed-measurement calls plus cold/repeated report costs. These are scalar-metric overhead workloads; the fixture's sample count is not an actual large-log decode. After real INI/MSQ/MLG loading and VE analysis, integrated checks require shell-owned INI/load/binding/restore metrics, Perf and Bug Report evidence, resource snapshots, no context mutation from opening reports and no rejected metadata records. Timing observations are not pass/fail thresholds or a substitute for representative target-hardware acceptance.

The installed lifecycle checks exercise the actual shell session, owner navigation/context evidence, unchanged-input suppression, legacy runtime-error/report projection, bounded Unicode errors, synthetic BFCache/visibility transitions and idempotent observed end. A real reload must create a new session with one start and no previous runtime errors. Synthetic lifecycle events test handler semantics; they do not prove actual BFCache eligibility or crash recovery. Expected synthetic error events remain visible to Vite; uncaught CDP exceptions still fail the runner.

Presentation checks create independent controllers and require help/formatting before observer delivery. They cover immediate Compare/Tune/Boost help and icon styling, Boost sorting/disclosures/empty feedback, rebuilt Idle/AE controls and help popovers, advanced-disclosure retention, Fueling table sorting by mouse/keyboard and summary help, final Histogram/Logger wording, synchronous lower-left VE geometry, and unrelated unowned DOM remaining untouched without additional analysis. These checks run against the actual application page in both import configurations. No production instrumentation is installed.

Each configuration first seeds synthetic workspace/catalog data, injects a throwing localStorage getter before a real page reload, checks complete bootstrap/navigation and in-memory INI import, then removes the injection and reloads to verify intact persisted data and healthy storage operations. The fault injection is confined to the isolated test context; production code has no test hooks.

Before the full-shell sequence, VE readiness checks cover the initial disabled gate, stable-duration blockers/Fix focus, shared status and unchanged snapshot identity, input/change invalidation, presentation-only table text, optional bounds/mixture mismatch, pending/inactive completion rejection, loaded availability/retry, unsubscribe and explicit delay recommendation activation.

Before the full-shell sequence, Math preview checks cover metadata-only edits/saves, coalesced typing/helper edits, immediate stale-load rejection, reset/hide/entry, and a 320459-sample input whose preview is capped at 10000 anchor samples while full logical analysis remains unbounded. A component Histogram workspace checks saved historical formulas in Table Generator, Math preview, Distribution and Scatter, including deduplicated dependencies, scoped coverage, missing-data recovery and stale preview rejection. Visible Math Channels create/edit/delete checks preserve field IDs, name/unit metadata, invalid-replacement rejection and consumer selector updates. The retired CSS-hidden Table formula editor must not be constructed. Visible persistence tests inject quota/security failures into Math Channels, Table presets, filter sets, Distribution presets and Scatter presets, checking session retention, actionable feedback, retry and current-cache safety. During full-shell setup, after INI/MSQ/MLG are loaded, the INI table-authority checks exercise preparation without publication, accepted replacement with stale persisted data and failed writes, navigation without storage reads, failed reads, empty definitions, unload, and explicit-context/tune mapping guards. The full-shell sequence loads INI, MSQ, MLG and a delay table through real file inputs, then enters VE and runs analysis before the replacement/navigation checks. Component fixtures exercise additional races and lifecycle transitions. No production instrumentation or application event listeners are installed by the runner.

MSQ acceptance checks also exercise single-pass entity decoding, literal entity text, supplementary characters, quoted numeric/empty/dimensioned strings, undimensioned metadata/vectors, finite numeric tables and rejection of mixed/NaN/infinite/blank numeric tables or blank dimensions. Full-shell failures for malformed numeric tables and invalid entities preserve the accepted tune, VE results, working delay and retained popup/evidence. Existing replacement generation/race checks still run.

The fixtures in `tests/fixtures/browser/` are the small synthetic fixtures from the earlier browser acceptance work. They contain generated channel data, a uniform 16×16 VE/AFR tune, and a uniform 100-ms delay table; they are not an owner's tune or recording. This suite is a correctness safety net, not a 1.2-GB log benchmark, original-recording acceptance, or exhaustive coverage of every browser module. Other `.browser.mjs` modules are not implicitly included. Vitest remains a separate command.

The Result View check follows the accepted policy: source-authoritative VE fallback values; original base heat in Proposed VE; neutral `0.5` heat for alternate views without the selected metric; interpolated delay values in Lambda Delay. Target 10 also asserts values and neutral fallback heat immediately after each selection event, before deferred corrections can run, then checks stable session revision, primary identity, zero primary-change notifications and no additional trace loading through repeated cycles. Existing lifecycle and delay-edit checks cover retained popup detail and working delays. The v7 Result View owner now commits text and heat together.

Results go to ignored `artifacts/browser/` (override with `BROWSER_RESULTS_DIR`). The runner replaces its own prior result files there. `summary.json` records success/failure and completed checks; per-suite JSON preserves named assertions and measurements. On browser failure it also attempts a screenshot and visible page snapshot. `chrome.log` captures startup/Chrome diagnostics. A missing executable, failed assertion, empty/malformed result, unhandled browser exception, timeout or interruption produces a nonzero exit; partial successes remain marked as a failed run. CI runs this command in the separate Web CI browser job and uploads the results even on failure.

Run CPU-heavy Vitest large-sample regressions separately from local browser/build work to avoid resource-contention timeouts. Passing this suite does not replace manual acceptance on representative logs and hardware.

Source-integrity integration target 1 retains all prior 514 checks and adds main's five marker checks per configuration: dotted bridge endpoints, click explanation, persistent notice, outside dismissal and zoom cutoff. These use synthetic graph data; original large-log and affected-hardware acceptance remain pending. Known metadata/algorithm/lifecycle follow-ups are listed separately in FIX_PLAN.md.
